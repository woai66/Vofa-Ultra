# 竞品与开源调研

调研基于 2026-08-26 可见的 VOFA+ 产品经验和
[Horldsence/vofa-NEXT](https://github.com/Horldsence/vofa-NEXT) 公开仓库。本文只记录工程决策依据，不对
其他项目作安全承诺或完整审计。

本次快照中 vofa-NEXT 有 7 个 open issue 和 2 个 open PR；数量会随上游变化，具体判断以下方链接内容为准。

## 值得继承的方向

| 方向 | 采用方式 |
| --- | --- |
| Rust 承担设备 I/O | 串口句柄和 worker 完全位于 Tauri 后端 |
| 字节平面与数值平面分离 | 原始终端与协议解析后的通道数据分别存储 |
| 高性能实时绘图 | 使用 uPlot，并限制每通道历史点数 |
| 大日志可用性 | 终端使用虚拟列表、单条展示上限、三种时间基准、字面量搜索和方向过滤 |
| 无硬件开发 | 模拟数据复用真实解析与自动应答入口 |
| 采集与视口解耦 | 暂停某个视图不会停止 RX 与统计 |
| 数值监视直达 | 基础、派生和扩展通道无需显示节点即可读取有界统计 |
| 可组合数据处理 | 固定节点 DAG 独立生成派生通道，不接管基础链路 |
| IMU 姿态可视化 | 先固定数据/坐标语义，再以 Three.js 呈现同解析帧姿态 |

[Issue #4](https://github.com/Horldsence/vofa-NEXT/issues/4) 说明只显示端口名不足以快速区分多个 USB 串口。
Vofa-Ultra 在冷启动、连接面板打开和窗口回到前台时进行有界枚举，按端口名自然排序，并显示产品、厂商与
VID:PID。当前选择暂时离线时不会被首个新端口替换；完整 USB 序列号不进入界面，只显示是否具备唯一身份。
后台枚举失败和生命周期变化后的迟到结果也不会覆盖当前连接状态。

控制线同样遵循单句柄模型：连接后可直接切换 DTR / RTS，但请求必须带当前连接代次并由唯一 Rust worker 执行，
驱动确认后界面才更新。硬件流控下不提供手动 RTS，文件发送和 Modbus 事务期间也不插入线路变化，避免便利控件
绕过串口任务边界。

底层读取 chunk 不是用户理解的文本行。Vofa-Ultra 因此把按 LF/CRLF/CR 聚合放在终端展示层：跨 chunk 的内容和
UTF-8/GB18030 多字节字符可以组成一条可读记录，Windows-1252 设备也可显式选择对应展示编码，但 parser、统计、
自动应答和 VUCAP 仍接收原始字节边界。未结束正文限制为
2,048 字节，避免错误行尾或二进制流让内存无限增长；终端仍使用原生文本选择和虚拟列表。这延续了“字节平面与
数值平面分离”及“采集与视口解耦”，而不是把可读性选项变成采集格式。

终端还区分绝对时钟、相对当前缓存首条记录和当前筛选结果的相邻记录间隔。相对基线不随筛选漂移，间隔也不依赖
虚拟列表当前挂载的 DOM 行；首条无前项和倒退时间都有明确显示。该选择不改变原始记录或 ISO 导出，因此可以直接
用于观察命令响应、周期抖动和异常空窗，而不会把临时分析视角误写进采集数据。

vofa-NEXT 的 [Issue #11](https://github.com/Horldsence/vofa-NEXT/issues/11) 强化了“采集继续、视口独立暂停”
这一方向。Vofa-Ultra 从首版就把它作为状态模型的一部分。

实时波形进一步区分“显式暂停缓存”和“缩放后挂起视口跟随”。用户沿 X 轴框选后，uPlot 固定 scale 并继续接收
2,000 点/通道上限内的全部保留数据，避免向前移动的时间窗立即清掉正在查看的区间；一键回到实时后再裁剪到当前
窗口。该交互不改变 `LIVE`、采集、解析、处理、终端、统计或录制，也不把临时视口写入工作区。

### 测量是显式视图模式

[Issue #10](https://github.com/Horldsence/vofa-NEXT/issues/10) 反映了图节点与显示控件关联时的交互和维护成本，
[Issue #11](https://github.com/Horldsence/vofa-NEXT/issues/11) 则说明冻结视口时持续采集是实际需求。Vofa-Ultra
把双游标测量设计为波形面板内的显式模式，不要求建立节点、连线或修改采集拓扑。开启后只冻结波形缓存，RX、
解析、处理、终端、统计和录制继续运行；退出时恢复用户进入测量前的暂停语义。

游标保存并吸附真实采样时间，图表 overlay 只负责坐标映射。测量不写入工作区，数据源、协议、处理图、工作区或
回放时间线改变时统一失效。这既保留快速读取 `Δt`、频率和 `Δy` 的工作流，也避免像素坐标、历史数据身份和长期
配置相互耦合。A/B 闭区间统计继续复用同一组真实采样锚点，只扫描单个有界通道并显示样本数、极值、均值、RMS
和峰峰值，因此不会为了分析读数扩大采集拓扑或持久状态。

### 基础数值监视不依赖显示节点

vofa-NEXT 提供 Gauge、NumberDisplay 和 Table 等显示控件，但基础数值观察仍与节点图的放置和连接关系绑定。
Vofa-Ultra 的“监视”直接消费已有基础、派生和扩展通道，以固定分组表格展示当前值、变化量、极值、均值、RMS
和样本数。用户不需要为了读数创建节点，也不会因显示布局改变采集拓扑。

统计按通道只查看最近 256 个源条目，冻结只保存组件快照，采集、处理、终端、记录和回放仍继续。数据流身份变化
会自动丢弃旧快照；窄屏收起次要列而不是把整个页面撑宽。这个设计保留了 VOFA+ / vofa-NEXT 快速读数的优点，
同时避开基础观察依赖图编辑、冻结误停采集和无界全历史扫描的问题。

### 解析失败必须可见

[Issue #10](https://github.com/Horldsence/vofa-NEXT/issues/10) 中“包含通道”检测失败的现象说明，只有“没有波形”
不足以区分设备无数据、帧尚未完成、协议选错和输入损坏。Vofa-Ultra 因此让 FireWater / JustFloat parser 输出
有界健康快照：成功、丢弃、重同步、稳定原因计数和最近失败时间。用户能在“通道”面板看到协议约束并清空统计，
结构化丢帧还会在状态栏留下紧凑警告；Raw Data 明确显示“不适用”。

诊断与协议状态机同源，所以同一坏单元无论如何分包只计一次，清空统计也不会破坏等待中的半帧。实时和回放使用
独立快照，视图暂停不停止统计，流边界会重置对应数据。实现不保存原始坏帧、不弹逐帧通知、不把运行计数写入
工作区，在可行动反馈、隐私和高频输入成本之间保持明确边界。

### 展示命名不污染数据身份

通道别名、单位和颜色是高频调试便利，但直接重写 parser 标签会让日志列名、姿态自动映射、处理图引用和回放
语义随界面编辑漂移。Vofa-Ultra 因此把 FireWater / JustFloat 的展示覆盖按协议和 `channel-0..15` 隔离保存，
运行时生成只供界面消费的投影。侧栏、波形、触发、测量、姿态菜单和处理图输入选择获得更可读的名称与颜色；
数值、稳定 ID、parser 原名、数值 CSV、VUCAP 和协议健康度保持原契约，单位也只标注而不换算。

这种分层还解决回放与实时协议错配：活动捕获协议决定展示配置，同编号通道不会从另一协议借用别名。该覆盖字段
自工作区 v10 起具有严格字段、字符串和颜色边界，旧工作区只补空配置；当前 v11 继续保留该语义，用户可恢复默认
而不会改写设备实际标签。

### 命令工作流不依赖节点图

vofa-NEXT 把命令发送器列为核心显示控件；其
[Issue #9](https://github.com/Horldsence/vofa-NEXT/issues/9) 也显示自动应答和命令类工作流是高频需求，但相关实现
受到后端图编译器性能与维护重构影响。Vofa-Ultra 把有界历史、可取消周期发送和 RX 自动应答做成独立基础能力，
直接复用统一发送仲裁、TX 回执和录制链路，不要求用户先创建节点图。自动应答只匹配静态 TEXT/HEX 字节串，
响应复用白名单模板；脚本、正则和任意变量表达式不混入这一基础层。

发送栏自动校验同样采用固定阶段而不是脚本：工作区 v11 严格保存 CRC-16/MODBUS、CRC-32 的两种字节序，以及
XOR-8、SUM-8 或关闭模式，并统一按“模板展开 payload、原始校验字节、TX 行尾”构帧。周期任务冻结启动时模式，
历史恢复实际模式；快捷命令仍只保存模板/格式/行尾并使用当前工作区设置。已经包含 CRC 的 Modbus 构帧结果会
主动关闭该模式，自动应答、Modbus 事务和原始文件发送则从结构上旁路，避免便利设置演变为隐式双重校验。

自动应答默认关闭且只响应实时 RX，回放从结构上旁路。跨 chunk 和重叠匹配不会依赖文本解码器，NUL 也可作为
触发字节；每条规则冷却、32 项 FIFO、单批 64 次命中和会话 1,000 次上限共同约束设备回显环路。手动发送在当前
自动写入完成后优先，周期发送则与自动应答互斥。这样吸收 Issue #9 的实际工作流价值，同时避免把不可信 RX
升级为脚本输入或让响应风暴占满发送通道。

Issue #9 同时提出 Modbus 发送。Vofa-Ultra 在可检查的 RTU 请求构帧器上增加受控的单事务主站，覆盖八种常用
读写功能码，并在前后端严格验证站号、0-based 地址、数量、末地址、广播、CRC 和多写字段。用户可选择只回填
HEX/无行尾草稿，也可执行一次关联事务；后者在唯一串口 worker 内等待 `t3.5`、完成写入和 flush 后启动超时，
支持跨分片、前置噪声、异常响应、CRC/回显错误与显式取消。原始 TX/RX 仍复用终端、统计和录制链路。

首版刻意保持单在途、有界观察和 32 条会话结果，不把轮询、自动重试、寄存器地图或 Modbus TCP 混入同一状态机。
这既补足“只能构帧、不能关联响应”的工作流缺口，也避免后台轮询与重试悄悄占用串口或让旧响应污染新连接。
浏览器模拟器只验证交互链路；RS-485 本地回显、半双工转向和真实设备时序仍要求硬件证据。

[Issue #6](https://github.com/Horldsence/vofa-NEXT/issues/6) 提出的字符串与数据互转同时包含手工排障和处理平面两种需求。
Vofa-Ultra 已把高频诊断部分做成独立工具：除 TEXT/HEX 帧校验外，还可在明确
`u8/i8/u16/i16/u32/i32/f32/f64` 和 LE/BE 的前提下执行 HEX 与数值列表互转，严格拒绝未对齐、越界和
非有限输入。这个手工工具不读取实时 RX、不改写处理图或发送草稿，也不自动发送数据。

处理图另以固定的 `bytes_to_number` 和 `number_to_byte` 节点承载实时数据语义：输入只取同一个完整解析帧，
缺失、非整数、越界或非有限值只让当前帧产生 gap，不跨帧拼接，也不进入 TX。配置经当前工作区 v11 持久化，历史
v1-v8 继续使用旧节点枚举严格迁移，v9 转换节点按当前枚举无损升级；运行时复用固定 8 字节缓冲，并由转换密集型性能预算约束同步 RX 热路径。
这样既覆盖 Issue #6 的手工排障与处理平面需求，也没有让弹层状态、原始字节流和处理 DAG 相互隐式耦合。

[PR #13](https://github.com/Horldsence/vofa-NEXT/pull/13) 暴露过文本拖选与行选择抢占导致复制错误的问题。Vofa-Ultra
的终端继续保留浏览器原生文本选择；命令历史导航只在输入框第一行或最后一行接管对应方向键，不改变终端记录的
选择语义。搜索只过滤和高亮当前 TEXT/HEX 可见负载，不用行点击模拟选择，也不把用户输入解释为正则表达式。

### 原始捕获与数值日志分层

[Issue #17](https://github.com/Horldsence/vofa-NEXT/issues/17) 同时提出实时保存原始数据和解析后 CSV；上游回复说明
解析日志受图编译器性能与维护重构阻塞。这是两个不同的数据契约。Vofa-Ultra 的 `.vucap` writer 和流式
CSV / JSONL 导出覆盖无损原始 RX / TX 记录；独立的实时数值 CSV 则在统一解析与处理入口记录基础/派生标量，
没有把 capture record 的十六进制 CSV 冒充解析日志。

数值日志采用固定 schema 的动态通道长表、前端与 Rust 双层有界队列和独立失败状态。基础值不依赖节点图，
派生值只按实际可用输出入表；波形暂停、显示环形缓冲和图层熔断不会阻塞基础数值。文件内容始终由 Rust 流式
写入 `.csv.part` 并在同步后原子提交，长期数据不驻留 WebView。这样吸收了 Issue #17 的用户价值，同时避开
上游把日志能力绑定图编译器的演进瓶颈。

VUCAP v2 还把命名时间线标记放入与 RX / TX 相同的有界 writer 和单调时钟，reader 继续兼容 v1/v2。回放只把
最多 512 个标记送到刻度与列表，不改变数据批次和 ACK；JSONL 按文件顺序保留标记，CSV/单向二进制则明确跳过，
避免为了一个界面功能破坏已有导出契约。

### 姿态视图先定义数据语义

[Issue #18](https://github.com/Horldsence/vofa-NEXT/issues/18) 希望 IMU 3D 姿态同时支持角度、弧度和四元数；上游维护者
表示计划在后续 prerelease 加入。Vofa-Ultra 没有把任意三个或四个 `lastValue` 直接交给 3D 模型，而是先固定
可验证的数据契约：Euler 输入明确为 Roll、Pitch、Yaw 和内禀 ZYX，单位显式选择 degrees/radians；四元数固定为
W、X、Y、Z，使用前归一化并拒绝非有限或模长过小的输入；坐标系成对选择 ENU 世界 / FLU 机体或 NED 世界 /
FRD 机体，避免只标“右手系”却仍留下世界轴、机体轴和分量顺序歧义。

基础与派生通道都可以参与映射，但处理输出保留批次内 `frameIndex`，提取器只组合来自同一个完整解析帧且时间戳
一致的值；两个帧即使时间戳相同也不会互相拼接。实时与回放复用同一提取路径，seek、重播、切换协议/数据源/
处理图/工作区会清除旧姿态。视图冻结只固定一个显示样本，采集、解析、处理、终端、统计、录制和回放继续运行，
归零与相机位置同样不污染持久配置。

Three.js 场景限制设备像素比并随容器调整尺寸，卸载时释放控制器、几何体、材质和 WebGL context；创建 WebGL
失败会显示明确降级状态，数值读数和其他工作台能力仍可用。这样实现的是带数据语义、生命周期和失败行为的调试
工具，而不是只追求一个会转动的演示模型。

### 调试器数据源先固定读权限与采样语义

[Issue #16](https://github.com/Horldsence/vofa-NEXT/issues/16) 希望从 ELF 符号选择变量，再通过 SWD/JTAG 探针进行
Live Watch，避免为观察 PID、传感器和状态变量额外编写串口输出。讨论还延伸到用 AI MCP 提高调试效率。这个方向
解决的是真实工作流，但它不是“再加一个 parser”：ELF/DWARF 类型、目标字节序、变量生命周期、探针驱动、目标
运行/暂停状态、读取对实时性的扰动、采样时间戳和与 IDE 争用都必须先有确定语义。

Vofa-Ultra 不会把探针 SDK、任意内存读取或模型指令直接放进主 WebView，也不会让当前仅消费实时 RX、零 import 的
`.vux` ABI 承担设备 I/O。后续评估应从只读、provider-neutral 的进程外适配器开始：每次会话显式授权固件与探针，
只允许固定标量类型和明确地址范围，限制采样率、批大小、队列和通道数，用单调时钟写入独立基础通道，并在断线、
固件身份变化或调试器争用时立即撤权。首版不写目标内存，也不把 AI 输出当作设备权限；MCP 若加入，只能调用同一套
可审计、有界、需确认的确定性操作。没有真实探针和目标板证据前，这一方向只保留为设计评估，不进入发布声明。

## 明确舍弃的做法

### 基础流程不依赖节点图

[Issue #2](https://github.com/Horldsence/vofa-NEXT/issues/2)、
[Issue #10](https://github.com/Horldsence/vofa-NEXT/issues/10) 和
[Issue #17](https://github.com/Horldsence/vofa-NEXT/issues/17) 展示了节点、图编译与基础工作流耦合后带来的
调试和演进成本：图编译器需要整体重构，平面图会放大通道轮询、控件关联、错误传播和连线交互问题，日志能力
也可能被底层图重构阻塞。Vofa-Ultra 的串口、协议、波形、终端、录制和导出始终是直接可用的稳定路径；处理图
只是协议帧之后的可选派生层。

首版因此采用列表式静态 DAG，而不是自由连线画布。节点与参数来自固定白名单，编译时验证引用与循环，运行时
限制节点、输出、滤波窗口和单批求值预算。配置失败保留旧图，运行异常只熔断派生层；基础通道不会被处理图
替换，实时和回放也不共享滤波状态。这保留了可组合处理的长处，同时缩小交互、性能和错误传播面。

### 不做过早的 crate 拆分

参考项目包含约 40 余个 crate。模块边界很有价值，但在行为尚未稳定时，大量 crate 会放大版本、编译和跨层
修改成本。Vofa-Ultra 当前保持单个 Rust crate，以传输、协议和 UI 的责任边界组织代码；只有出现独立发布、
独立测试或显著编译收益时才拆分。

### 主 WebView 不运行动态代码

调研时观察到参考实现使用宽松 CSP、较宽文件权限，以及主 WebView 中的动态字符串执行路径。这些设计并不
自动等同于可利用漏洞，但会扩大攻击面和诊断难度。Vofa-Ultra 使用非空严格 CSP、最小 capability，不使用
`eval` / `new Function`。当前实验性 `.vux` 只在 Rust 主进程的零 import Wasmi 解释器中运行，不向 WebView
注入代码；它仍是进程内边界，不能描述为完整 OS 沙箱。

### 不使用透明主窗口

透明窗口增加跨平台合成差异、文字对比度问题和 GPU 故障排查成本，却不改善串口工作流。Vofa-Ultra 使用
不透明、系统装饰的工作型界面。

## 从 Issues 与 PR 学到的发布纪律

- [PR #5](https://github.com/Horldsence/vofa-NEXT/pull/5) 表明，状态已经更新不代表用户能看见选择结果；互相冲突的
  样式类会让选中态被普通态覆盖。Vofa-Ultra 的模式按钮使用互斥状态样式和 `aria-pressed`，行尾等选项优先使用
  原生选择控件，组件测试同时断言状态语义与交互结果。
- [PR #14](https://github.com/Horldsence/vofa-NEXT/pull/14) 提醒我们：测试必须固定面向用户的正确语义，
  不能只固定当前实现产生的错误结果。
- 调研时 [PR #13](https://github.com/Horldsence/vofa-NEXT/pull/13) 与
  [PR #15](https://github.com/Horldsence/vofa-NEXT/pull/15) 均仍为 Draft；其中 PR #15 暴露了普通 PR 构建与签名
  发布边界不清的问题。Vofa-Ultra 当前不启用线上发布自动化；未来若恢复，签名材料必须与普通 PR 完全隔离。
- 当前由维护者本地执行构建、协议测试和真实页面验收；未来自动化也不能只验证某一层“能编译”。

## 许可证边界

调研时 vofa-NEXT 仓库的 `LICENSE` 为 GPL-2.0，而 README 标注 MIT。遇到许可证元数据不一致时，应按更
保守的边界处理并向上游确认。

Vofa-Ultra 只学习公开的产品与架构思想，代码和视觉实现均为独立创作，不复制参考项目源码、资源或受保护
表达。贡献者不得直接粘贴来源不明或许可证不兼容的代码。

## 衡量“更好用”

“超过”不是功能数量竞赛，而是用可验证指标持续改善：

- 基础连接、收发和断线恢复不依赖高级功能。
- 长时间运行时内存有上限，UI 节点数不随日志无限增长。
- 错误包含可行动的信息，连接状态不会因异步乱序倒退。
- 无硬件也能复现完整数据链路，真实硬件场景有发布前测试矩阵。
- 默认权限最小，第三方扩展不能向主 WebView 注入代码，动态能力必须显式授权和版本化。
- 文档、测试、许可证、本地构建与发布产物保持一致。
