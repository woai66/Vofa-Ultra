# 竞品与开源调研

调研基于 2026-08-24 可见的 VOFA+ 产品经验和
[Horldsence/vofa-NEXT](https://github.com/Horldsence/vofa-NEXT) 公开仓库。本文只记录工程决策依据，不对
其他项目作安全承诺或完整审计。

## 值得继承的方向

| 方向 | 采用方式 |
| --- | --- |
| Rust 承担设备 I/O | 串口句柄和 worker 完全位于 Tauri 后端 |
| 字节平面与数值平面分离 | 原始终端与协议解析后的通道数据分别存储 |
| 高性能实时绘图 | 使用 uPlot，并限制每通道历史点数 |
| 大日志可用性 | 终端使用虚拟列表和单条展示上限 |
| 无硬件开发 | 模拟数据复用真实解析入口 |
| 采集与视口解耦 | 暂停某个视图不会停止 RX 与统计 |
| 可组合数据处理 | 固定节点 DAG 独立生成派生通道，不接管基础链路 |

vofa-NEXT 的 [Issue #11](https://github.com/Horldsence/vofa-NEXT/issues/11) 强化了“采集继续、视口独立暂停”
这一方向。Vofa-Ultra 从首版就把它作为状态模型的一部分。

### 测量是显式视图模式

[Issue #10](https://github.com/Horldsence/vofa-NEXT/issues/10) 反映了图节点与显示控件关联时的交互和维护成本，
[Issue #11](https://github.com/Horldsence/vofa-NEXT/issues/11) 则说明冻结视口时持续采集是实际需求。Vofa-Ultra
把双游标测量设计为波形面板内的显式模式，不要求建立节点、连线或修改采集拓扑。开启后只冻结波形缓存，RX、
解析、处理、终端、统计和录制继续运行；退出时恢复用户进入测量前的暂停语义。

游标保存并吸附真实采样时间，图表 overlay 只负责坐标映射。测量不写入工作区，数据源、协议、处理图、工作区或
回放时间线改变时统一失效。这既保留快速读取 `Δt`、频率和 `Δy` 的工作流，也避免像素坐标、历史数据身份和长期
配置相互耦合。

### 命令工作流不依赖节点图

vofa-NEXT 把命令发送器列为核心显示控件；其
[Issue #9](https://github.com/Horldsence/vofa-NEXT/issues/9) 也显示自动应答和命令类工作流是高频需求，但相关实现
受到后端图编译器性能与维护重构影响。Vofa-Ultra 先把有界历史和可取消周期发送做成独立基础能力，直接复用统一
发送队列、TX 回执和录制链路，不要求用户先创建节点图。自动应答、脚本和任意变量表达式不混入这一基础层。

[PR #13](https://github.com/Horldsence/vofa-NEXT/pull/13) 暴露过文本拖选与行选择抢占导致复制错误的问题。Vofa-Ultra
的终端继续保留浏览器原生文本选择；命令历史导航只在输入框第一行或最后一行接管对应方向键，不改变终端记录的
选择语义。

## 明确舍弃的做法

### 基础流程不依赖节点图

[Issue #2](https://github.com/Horldsence/vofa-NEXT/issues/2)、
[Issue #10](https://github.com/Horldsence/vofa-NEXT/issues/10) 和
[Issue #17](https://github.com/Horldsence/vofa-NEXT/issues/17) 展示了节点、图编译与基础工作流耦合后带来的
调试和演进成本：图编译器需要整体重构，平面图会放大通道轮询、控件关联、错误传播和连线交互问题，日志能力
也可能被底层图重构阻塞。Vofa-Ultra 的串口、协议、波形、终端、录制和导出始终是直接可用的稳定路径；处理图
只是协议帧之后的可选派生层。

首版因此采用列表式静态 DAG，而不是自由连线画布。节点与参数来自固定白名单，编译时验证引用与循环，运行时
限制节点、输出、滤波窗口和单批求值预算。配置失败保留旧图，运行异常只熔断派生层；基础通道不会被处理图
替换，实时和回放也不共享滤波状态。这保留了可组合处理的长处，同时缩小交互、性能和错误传播面。

### 不做过早的 crate 拆分

参考项目包含约 40 余个 crate。模块边界很有价值，但在行为尚未稳定时，大量 crate 会放大版本、编译和跨层
修改成本。Vofa-Ultra 当前保持单个 Rust crate，以传输、协议和 UI 的责任边界组织代码；只有出现独立发布、
独立测试或显著编译收益时才拆分。

### 主 WebView 不运行动态代码

调研时观察到参考实现使用宽松 CSP、较宽文件权限，以及主 WebView 中的动态字符串执行路径。这些设计并不
自动等同于可利用漏洞，但会扩大攻击面和诊断难度。Vofa-Ultra 使用非空严格 CSP、最小 capability，不使用
`eval` / `new Function`，后续第三方扩展也必须进入受限边界。

### 不使用透明主窗口

透明窗口增加跨平台合成差异、文字对比度问题和 GPU 故障排查成本，却不改善串口工作流。Vofa-Ultra 使用
不透明、系统装饰的工作型界面。

## 从 Issues 与 PR 学到的发布纪律

- [PR #14](https://github.com/Horldsence/vofa-NEXT/pull/14) 提醒我们：测试必须固定面向用户的正确语义，
  不能只固定当前实现产生的错误结果。
- [PR #15](https://github.com/Horldsence/vofa-NEXT/pull/15) 暴露了普通 PR 构建与签名发布边界不清的问题。
  Vofa-Ultra 的常规 CI 不读取签名材料；正式发布工作流将使用受保护环境并与 PR 完全分离。
- CI 必须覆盖构建、协议测试和真实页面验收，不能只验证某一层“能编译”。

## 许可证边界

调研时 vofa-NEXT 仓库的 `LICENSE` 为 GPL-2.0，而 README 标注 MIT。遇到许可证元数据不一致时，应按更
保守的边界处理并向上游确认。

Vofa-Ultra 只学习公开的产品与架构思想，代码和视觉实现均为独立创作，不复制参考项目源码、资源或受保护
表达。贡献者不得直接粘贴来源不明或许可证不兼容的代码。

## 衡量“更好用”

“超过”不是功能数量竞赛，而是用可验证指标持续改善：

- 基础连接、收发和断线恢复不依赖高级功能。
- 长时间运行时内存有上限，UI 节点数不随日志无限增长。
- 错误包含可行动的信息，连接状态不会因异步乱序倒退。
- 无硬件也能复现完整数据链路，真实硬件场景有发布前测试矩阵。
- 默认权限最小，第三方扩展不能直接扩大主窗口攻击面。
- 文档、测试、许可证、CI 与发布产物保持一致。
